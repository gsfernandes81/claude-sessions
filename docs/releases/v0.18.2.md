## Agent messaging: offloaded sessions woken by a message, and every agent told what that costs

- **A message to an offloaded session wakes it, where its container has room** for one more
  session (about 250 MB, the menu's own rule). It resumes headless, in the remote view, until
  it has been quiet for 10 minutes and is offloaded again, and the message is delivered once it
  is up. Without room, or with its container down, the message is kept (up to 7 days), as
  before.
- **The sender is told what happened** by a notice from `hub/router`: woken, with the memory
  it costs and what was free; not woken and why; or its container not answering.
- **An offloaded session no longer shows as idle in ListAgents.** It is listed with no status:
  Claude Code shows only its own status words, so it cannot say "offloaded".
- **Every session is told, at its start and again after a compaction, what that means**: no
  status is offloaded, waking one costs RAM and CPU on the shared host, so prefer a live peer
  and send one message, not several. It is four lines of context, given by a new
  `peer-context` SessionStart handler.

For infra:

- **The drop-in gains a second `SessionStart` handler**: `<bin> peer-context`, synchronous,
  timeout 5 s. The registry hook is unchanged and still silent. `peer-context` is the one
  handler that speaks, and says only its line. It always exits 0, says nothing to a subagent,
  and is built from constants: no registry, no network. `crossSessionInbound` is unchanged.
  Please update the hooks row in your README and the drop-in row in decisions.md.
- **Your three checks, against Claude Code 2.1.311** (2026-11-07). Each is also held by a test
  in `tests/claude_peer.rs` against the real binary, run in CI at `CLAUDE_CODE_VERSION`:
  1. A SessionStart hook's `additionalContext` reaches the model under `claude -p`, as the
     holder runs it. Measured with the hook given by `--settings`, the same hook machinery as
     the managed drop-in. The test passes our shipped `hooks-config` output as the settings.
  2. After a compaction, SessionStart fires again with source `compact`, and the context is
     back in the next request. The test checks this in a request from which the first prompt
     has been compacted away.
  3. A SessionStart hook that exits 1, or hangs past its timeout, does not stop the start:
     claude started and answered in both cases. Separately, `tests/hook_contract.rs` holds
     `peer-context` to exit 0 whatever it is fed, a closed stdout included.
- **No new volume, variable or skill.** The `peers` skill on main for a while never shipped.
- **Waking uses the remote view's resume** (`remote open`), so a woken slot is driven by the
  holder, as when the owner opens it from the phone. No compose change.
