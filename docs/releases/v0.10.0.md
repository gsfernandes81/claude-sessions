## pi as a second harness: `pi-<n>` slots

Built to the owner's brief of 2026-10-30, relayed and agreed by infra's agent. The
specification is `docs/design.md` § *Harnesses*; this is what infra's base, entrypoint and
`make verify` are written against. Nothing changes for a claude slot.

**What a pi slot is.** A `zmx` session `pi-<n>` running
`pi --session-id <id> --tui-mode regular` in the workspace, under `CLAUDE_SESSIONS_SLOT=pi-<n>`
and nothing else of ours in its environment. The id is a UUID the launcher makes and writes
into the slot's record with the cwd before zmx runs, so the slot is resumable from the record
alone; a resume is the same line in the recorded cwd. `--tui-mode regular` is the twin of the
three `CLAUDE_CODE_DISABLE_*` variables: pi's default `fullscreen` mode takes the alternate
screen and mouse tracking, the combination issue #8 removed from claude.

**What infra sets and links:**

| | |
|---|---|
| `PI_CODING_AGENT_DIR` | where pi keeps its sessions (`<dir>/sessions/--<cwd>--/…jsonl`); read by the menu for Archived and for a slot's conversation. Default `~/.pi/agent`. `PI_CODING_AGENT_SESSION_DIR` is honoured as pi honours it |
| `CLAUDE_SESSIONS_PI` | the pi to run, if not `pi` on `PATH`; beside `CLAUDE_SESSIONS_CLAUDE` |
| `/opt/claude-sessions/extensions/claude-sessions.js` | written by `install` (also printed by `claude-sessions pi-extension [path]`), with the binary's path in it; link it into `$PI_CODING_AGENT_DIR/extensions/` at every container start, as the skills are linked. Without it a pi slot starts, lists, resumes and archives, but is never bound, so never offloaded |
| `tuiMode: regular` | in the baked settings, so a `pi` from a shell scrolls as the menu's does |

**The extension** feeds `claude-sessions hook` one JSON body per event on stdin, `pi_event`
in place of `hook_event_name`, from node's own `child_process`, and the hook reads it as the
row of the event table it means: `session_start` → `SessionStart`; `before_agent_start` →
`UserPromptSubmit`; `agent_settled` → `Stop`; `ui_prompt_start` → the amber `!`;
`ui_prompt_end` clears it; `session_shutdown` quit → `SessionEnd`; `session_info_changed` →
the title. Binding is the same `/proc` walk as claude's, with comm `pi` admitted, so a pi
nested under a tool call never rebinds a slot.

**The menu:** `p` starts a pi session beside `n`'s claude, at the home in the cursor's
container; a pi row carries a dim `pi: ` before its title; Archived lists pi's conversations
with claude's, and `Enter` on one resumes it in a `pi-<n>`. A 0.9.0 hub against this agent
draws pi rows plainly and cannot start one; this hub against a 0.9.0 agent gets `p` refused
rather than a claude slot (`new_pi`, `offload_then_open_pi` are ops an older agent does not
know).

**Mail:** `<repo>/pi-<n>` is an address like any other once the container's agent lists the
slot live. No nudge into a pi slot; infra's policy has pi run `claude-sessions mail list`.

**The offload rule is unchanged**; the orphan sweep has no pi rule, since pi starts no daemon
that was found. **Not measured here:** pi's `/proc/<pid>/comm`, idle CPU and RSS, and what
survives a TERM — infra's smoke run against this tag reports them, and the two checks asked
for are that a pi slot's record gets a `pid` and `hook.log` stays empty.
